# 40 加上以太网传输能解决什么（方案与边界）

> 2026-11-02 · 输入：用户问题（m00116）「加上以太网传输，能解决哪些问题？在不影响现有功能的情况下，可以动程序」
> 只读结论，未改代码。配套 [`39_host_improvement_plan.md`](39_host_improvement_plan.md) 的 C1 项。

---

## 0. 先分清两件不一样的事

| | 现在的以太网 | "加以太网传输" |
| --- | --- | --- |
| 传什么 | **只有抓包缓冲**（28672 点样点，或连续流的 (s,c) 样点对） | 还要传**遥测 18 B 帧**（角度/转速/状态） |
| 谁在用 | 抓包页的「网口 UDP / 网口连续流」两个下拉项 | 全软件的数据源，含转速、位置、告警、波形 |
| 配置通道 | **仍然是串口**（`docs/22:11`「配置和寄存器仍然走串口」） | 可选：串口做配置，网口做数据（推荐） |
| 板端改动 | 已实现（`rtl/eth/`：`eth_top.v` 33.8 KB、`scope_udp.v` 24.5 KB、`stream_tx.v` 18.4 KB、`eth_reply.v` 17.9 KB） | 需新增"遥测帧打包 + 高频小包发送" |

**换句话说**：以太网在板子上已经通了，但它现在只被当成"一个更快的抓包口"，没被当成"数据主干"。下面说的价值，全部来自把它变成主干。

---

## 1. 直接解决的六个问题（都是现在真实存在的）

### 1.1 带宽：90% → 0.14%，遥测率可以提一个数量级

| | 串口 | 千兆 UDP |
| --- | --- | --- |
| 18 B × 10 kHz | 180 kB/s，占 2 Mbaud 的 **90%**，余量 ≈18 kB/s | 1.44 Mbps，占 **0.14%** |
| 18 B × 100 kHz | **不可能**（需 1.44 MB/s > 200 kB/s） | 14.4 Mbps，占 1.4% |
| 加 4 B 字段 | +22% 占用 ⇒ 直接崩 | 无所谓 |

**意义**：现在"不敢加字段"的约束消失。每帧可以免费带上幅值、正交误差、偏置、锁定状态、前馈修正量、LUT 索引——**A3 那条"2 s 轮询 8 条读命令"的卡片，变成每帧自带，轮询归零**。
遥测率提到 50-100 kHz 后，时间分辨率从 0.1 ms 到 10-20 µs：转速波动、齿槽、位置环振荡第一次能看清。

### 1.2 误码：0.38% 校验错归零，两个补丁可以退化成兜底

现在 `link.py` 为了对付 0.38% 的 XOR 校验错，做了三件复杂的事：重同步（`_find_sync`/`_skip_to_sync`）、丢帧计入帧时隙（`n_bad` 补偿）、频率必须"整数电周期 + 小数残差"合成（否则虚高 0.8%）。

以太网链路上有 **FCS（CRC32）**，误码率量级 1e-12，且丢包是"整包丢"而不是"丢半个帧导致后续帧全部错位"。于是：
- 0.8% 频率虚高的隐患从"设计约束"降级为"降级路径的注意事项"；
- `n_bad`/`n_drop` 的结账逻辑可以简化为"包序号缺口"；
- 一台机器上最容易变成"玄学"的那部分代码（重同步）不再天天被走到。

**但不能说"彻底不丢"**，见 §3.1。

### 1.3 延迟：0.66 s → 2 ms，调参手感完全不同

| 通道 | 一次 28672 点 | 倍率 |
| --- | --- | --- |
| 串口回读 | ≈0.66 s（448 块） | 1× |
| 网口 UDP | ≈2 ms（82 包） | **≈330×** |

现在改一个倍频/极对数，要等半秒到一秒才能看见波形变；有了网口，改完立刻见。**这对"现场调参"的体验是质变**，也是把上位机从"观测工具"变成"调试工具"的分界线。

### 1.4 抗干扰与距离：这条比带宽更值钱

现场是电机转台：PWM、变频器、长线。那 0.38% 误码的来源大概率就是 **CH340 + USB 线**在强干扰下的共模问题。

- 网线是**差分 + 变压器隔离**，天然抗共模；
- 可拉 **100 m**，PC 能离开隔振台/屏蔽间，放到操作间；
- 不用再担心 USB 口松动、COM 号漂移、驱动装不上。

**这条是"稳定性"的直接来源，不是"性能"。**

### 1.5 轮询消除：状态从"每 2 s 问一次"变成"跟着帧来"

现在 `_tick_body()` 里 `STATUS_PERIOD_S` 每 2 s 读 8 条寄存器（注释写"≈3 ms 链路时间"）。这 8 条读命令在 90% 占用的链路上是**实打实抢遥测带宽**的。网口后可以完全去掉。

### 1.6 标定提速：LUT 上传从 10-30 s 降到 1 s 级

4096 点 × 2 次写 = 8192 次寄存器事务。串口按 ≈1.2 ms/次估 = **10-30 s**。若命令通道也走网口（一次 UDP 请求/应答 ≈0.2 ms 往返），可降到 **<2 s**。
这直接把 39 号文档里的 B2（全周误差表向导）从"要进度条、要断点续传"变成"点一下就好"。

## 2. 解锁的四个新能力（其中三个要动 RTL）

### 2.1 ✅ 只有上位机：真正的时域波形（不再混叠）

现在 10 kHz 遥测对 50 kHz 输入是**必然混叠**的（`host/README.md` 自己写了"看李萨如圆度"）。而网口连续流送的是 **12.5 MSPS 的 (s,c) 样点对**，是未经抽取的真信号。

**关键发现：板子和协议都够用，瓶颈在软件。**
- `stream_capture.py:85` `history = 1 << 18` = **262144 点**环形缓冲，早就在了；
- 但 `main_window.py:1920` 只 `snapshot(1024)`，即**只画最近 1024 点**；
- 原因写在注释里（`main_window.py:1904-1906`）：**"画 4096 点一次要几十毫秒，期间收包线程拿不到 GIL，62.5k 包/s 会把 4 MB socket 缓冲冲爆（实测丢 39% 的包）"**。

⇒ 所以"看真实波形"这件事，**不需要新硬件，只需要把绘图与接收解耦**（包络降采样到 ≈2000 像素 + 只在可见时画 + blit）。这是性价比最高的一步，而且与以太网遥测互不依赖。

### 2.2 ✅ 只有上位机：FFT / 谐波 / 阶次分析

有了 12.5 MSPS 真样点，`numpy.fft`（现在 **0 处**）才第一次有意义：1×/2×/3× 谐波、齿槽频率、PWM 干扰谱、编码器残余误差的频谱特征。
**这是"精度问题"从"猜"变成"定位"的关键**，而且全在上位机做，不碰 RTL。

### 2.3 ⚠️ 要 RTL：遥测帧走 UDP（100 kHz 小包）

板端要做"18 B 帧打包器"（把 ~150 帧塞进一个 2.7 kB 的 UDP 包）+ 发送调度。现有 `stream_tx.v` 是"样点流"，格式完全不同，不能复用。
**工作量估**：RTL 2-3 周 + 上位机 1 周。

### 2.4 ⚠️ 要 RTL：深窗 + 触发（DDR 缓冲）

`docs/18_streaming_ddr_plan.md` 已有规划。有了它才能做"连续 10 s 波形 + 上升沿触发 + 回溯"，把抓包从 1.15 ms 的"看一瞬"变成"看全过程"。

## 3. 以太网解决不了什么（先说清楚，免得后面返工）

### 3.1 不能保证"不丢"

UDP 无重传、无有序交付。丢包来源：网卡节能（Windows「绿色以太网」）、CPU 忙、交换机缓冲、突发。**必须每包带序号**（现有 dump 的"缺块"标注方向是对的），关键用途（标定采点）要加"整窗校验 + 重传请求"。

### 3.2 时间戳精度不会变好

以太网不提供硬实时；跨帧时间仍靠主机 `time.monotonic()`，jitter 取决于 OS。要精确测频，**仍然以板上帧计数为主时钟**——这一点现在的设计是对的，不要因为换了链路就改。

### 3.3 配置通道仍是串口（除非额外做 UDP 命令通道）

这是现状设计（`docs/22:11`），也是**合理设计**：串口是有应答、可重试的可靠小事务通道，正好配寄存器读写；网口是无连接大吞吐。**别为了"一根线"把可靠通道改成 UDP**，成本高、收益低。

### 3.4 现场网络会变成新的"电话支持"来源

`docs/22:91-105` 已经列了 10 条故障现象：ping 不通、ARP ✗、主机 MAC ✗、缺块 40+、百兆、WLAN 抢路由、防火墙、端口被 Vivado 占用、首次丢 40 块（host_mac=0）、RGMII 延时。
**"插上网线就能用"是不成立的**。所以必须配：一键自检（已有）、**自动发现板子**（UDP 广播探测，现在没有）、通道健康指示、自动降级。否则引入以太网等于把"零配置"变成"要配 IP"。

### 3.5 百兆口/笔记本 USB 网卡

千兆是硬要求（`docs/22:25`「百兆会大面积丢包」）。很多工控机只有百兆。所以：**遥测走网口可以（1.4 Mbps 百兆也够），连续流/波形不可以**。程序必须按实际 LinkSpeed 自动决定"哪些能力可用"。

### 3.6 一条会放大的旧问题

现在 CSV 是 **40 MB/min**。遥测提到 100 kHz = 400 MB/min；连续流记录 12.5 MSPS = 3 GB/min。**带宽提升会立刻把存储问题放大 10 倍**，所以 39 号文档的 B4（二进制记录 + 元数据）必须与以太网同步做，不能等。

## 4. 程序侧怎么改（"不影响现有功能"的工程保障）

### 4.1 现状的耦合点

`link.SerialWorker` 一个类干三件事，全绑在串口上：

| 职责 | 方法 | 网口化难度 |
| --- | --- | --- |
| 字节流接收/帧同步/解析 | `run`/`_loop`/`_pump`/`_find_sync` | **纯逻辑，可直接复用** |
| 命令事务（4 B → 6 B） | `transact`/`read_reg`/`write_reg`/`_execute_seq` | 先留在串口 |
| 抓包 dump 状态机 | `_pump_dump`/`capture_*` | 已另有 `udp_capture.py`，重复度低 |

### 4.2 改造：抽 `Transport`，其余不动

```
Transport（新，抽象）
 ├─ SerialTransport   ← 现在 SerialWorker 里的 open/read/write 部分原样搬过去
 └─ UdpTransport      ← 新：recvfrom → 拆包 → 送进同一个解析器

TelemetryParser（新，纯函数）  ← 从 _find_sync/_pump 抽出来，UDP/回放/串口共用
CommandChannel（不变）         ← 仍然只有串口实现
```

**关键约束：新类与旧类 API 同形。** `MainWindow` 只依赖 `worker.events`（队列）、`worker.transact()`、`worker.counters()`、`worker.stop()`。只要新类实现这四个，**UI 一行不改**——这就是"不影响现有功能"的保证方式。

### 4.3 三通道并存 + 自动降级

| 场景 | 行为 |
| --- | --- |
| 只插串口 | 今天的行为，一字不变（**这条是回归基线**） |
| 串口 + 网线，自检通过 | 遥测走网口，配置/LUT 走串口；UI 顶栏显示「数据: 网口 ｜ 配置: 串口」 |
| 网口 3 s 无包 | 自动回串口，**不弹框**，只记一条 warn（复用 `_watch_link` 的静默机制） |
| 网口恢复 | 不自动切回（避免来回跳），由用户点「切到网口」或下次启动 |

### 4.4 门禁（怎么证明没破坏现有功能）

1. 现有 277 项 `selftest_ui` + 7 个模块 `--selftest` 必须全绿（`tools/check_offline.ps1`）；
2. 新增：`TelemetryParser` 用**录制的真实 18 B 字节流**做 golden fixture（现在 `selftest_link` 是手工造帧，缺真实流量）；
3. 新增：`SerialTransport` 与 `UdpTransport` 喂同一段字节流，解析结果必须**逐字段相等**（差分测试）；
4. `tools/fuzz_host_protocols.py` 扩展到 UDP 包（截断/超长/错 magic/错序号）。

## 5. 分阶段（按"要先解决什么"排，不按工作量排）

| 阶段 | 内容 | 动哪里 | 工作量 | 依赖 |
| --- | --- | --- | --- | --- |
| **E0** | **接收/绘图解耦**：包络降采样、可见性门控、blit。让连续流从"1024 点 / 300 ms / 丢千分之几"变成"整窗 262k 点 / 30-60 FPS" | 纯上位机 | 4-5 d | 无 |
| **E1** | **真波形页**：连续流接入主波形（触发对齐 + 一屏整电周期），加 FFT/谐波面板 | 纯上位机 | 4 d | E0 |
| **E2** | `Transport` 抽象 + `UdpTransport` 遥测接收（**板端已有帧流才能用**） | 上位机 1 w | 1 w | RTL 遥测打包 |
| **E3** | 遥测 100 kHz + 每帧带状态字段（轮询归零） | RTL 2-3 w + 上位机 3 d | 3 w | E2 |
| **E4** | UDP 命令通道（LUT 秒级）+ 深窗/触发（DDR） | RTL | 3-4 w | E3 |

**注意 E0 的位置**：它排在最前面，不是因为它最简单，而是因为**不先做它，后面所有带宽都是白给**——现在的软件连 12.5 MSPS 都接不住（实测丢 39% 包），再加 100 kHz 遥测只会更糟。

## 6. 一句话总结

以太网真正带来的**不是"更快"，是"敢用"**：

- **敢加字段**（带宽从 90% 到 0.14%）；
- **敢提速率**（10 kHz → 100 kHz，时间分辨率 ×10）；
- **敢看真波形**（混叠消失，FFT 才有意义）；
- **敢放远**（100 m + 隔离，抗干扰）；
- **敢秒传标定表**（30 s → 1 s）。

它**不解决**：丢包、实时性、配置简化、现场网络复杂度。而且有两件事必须先于它：**接收/绘图解耦**（E0）和**二进制记录**（39 号 B4），否则带宽提上去只会把老问题放大。

## 7. 需要你确认的三件事

1. **RTL 能不能排进 2-3 周**？E2/E3 全靠它。不能的话，以太网就只剩"抓包更快"这一层价值（E0/E1），也值得做，但不要指望它解决遥测带宽。
2. **现场是直连还是过交换机**？直连最稳（自动发现可以简化为固定 IP）；过交换机要处理 DHCP/网段冲突。
3. **目标工控机有千兆口吗**？没有的话，E1 之后的连续流方案要改成"降低抽取比 + 更短窗口"，能力打折。
