# P6 · 从 .hwh 与 IP 手册推导寄存器映射

**适用**：手上有一个 `.hwh`（或 `.xsa` 里的 handoff）和一堆 IP，要写出 Python 侧的
访问代码；最容易出错的地方是**把"地址段"当成"寄存器偏移"**。

**不要这样问**（会稳定地得到幻觉）：

> "帮我写这个项目的 PYNQ 驱动。"

模型没有任何依据，会把偏移编成 0x00/0x04/0x08 的整齐表格，而且语气非常肯定。

**这样问**（把事实与推理分开，并要求它自己标出不确定的地方）：

```text
下面是 VIVADO 2026.1 导出的 .hwh 文本（<粘贴全文>）与我要驱动的 IP 手册片段（<贴片段>）。

请只根据这两份材料，输出三样东西：

1. 一张地址表：实例名 | 基址(hex) | 长度 | 来自 hwh 的哪个节点/属性。
   凡 hwh 里没有的，写"hwh 未提供"，不要补。
2. 一张寄存器表：偏移 | 名称 | 位域名 | 读/写 | 依据（手册的哪一页/哪一节）。
   如果手册没写某个偏移，这一行写"手册未定义"，不要猜。
3. 一段最小访问代码：只用 pynq.Overlay + mmio，包含
   - 一个"读回常量"的上电自检（例如读 ID 寄存器，期望值写在注释里）；
   - 一次 Walking-ones 写读回环；
   - 每次寄存器写入后的读回断言。
   代码里不许出现 hwh 与手册之外的地址常量。

最后单独列一段"我不确定的地方"，每条写明"缺什么信息才能确定"。
```

**为什么要分三步**：地址是**文件里的事实**（可被 `pynq_hwh.py` 机械核对），
寄存器偏移是**文档里的事实**（只能引页引节），代码是**两者的组合**。
把三类事实混在一次回答里，模型就会用编造补齐空缺——本工程的记录 19（注释引用不存在的
SPEC 章节）与记录 70（注释写清理由≠欠账被记住）都是这么来的。

**验收**：

1. 地址表必须能被 `python skill/pynq/pynq_hwh.py x.hwh --md` 的输出逐行对上；
2. 寄存器表每一行都要能指到手册页；指不到的，删掉；
3. 代码里"读回常量"那条判据必须真的在板上跑过——它是后面所有调试的前提。

**失效条件**：IP 手册不公开（加密/私有）时第 2 步做不出来，只能退化成"以 RTL 为准"，
那就改问："根据这段 RTL 的寄存器写逻辑，列出偏移与位域"，并把 RTL 片段一起贴进去。
