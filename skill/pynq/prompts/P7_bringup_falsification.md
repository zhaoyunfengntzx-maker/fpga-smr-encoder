# P7 · 上板前的"证伪"清单

**适用**：overlay 下载成功、判据也过了，但你**还没**确认这些判据真的能失败。
上板调试最贵的错误是"判据永远为真"——它比没有判据更糟，因为你会拿它当证据。

**固定的两轮问法**（照 `skill/prompts/P3_testbench_falsification.md` 的结构，只是对象换成板子）：

### 第一轮：列出"能让你的判据通过的最小改动"

```text
下面是我在板上跑的自检（<贴 5 条判据的代码与最近一次输出>）。

任务：假设你是来找茬的。不要评价代码风格，只回答一件事——
分别修改**一个**东西，让这 5 条判据**全部仍然 PASS**，但功能其实是错的。
每条给出：改动点（哪个寄存器/哪根线/哪行代码）+ 为什么判据抓不到 + 需要在判据里加什么才能抓到。
至少给 4 条，按"最容易发生"排序。
```

典型答案（本工程在测试台阶段真实遇到过的形状）：

- 把 PL 的输入常量化，输出只接常量 → "逐点比对"如果期望表也是常数就会过；
- 把 `COUNT` 寄存器接成常量 1024 → "计数一致"那条永远过；
- DMA 只搬前 8 个字节，判据只查长度不查内容 → 长度对、内容错；
- 地址没解对时读回全 0，而期望值也允许 0（例如对全 0 输入做直通）→ 恰好通过。

### 第二轮：真的改一处，看判据会不会红

```text
现在我把 <某个改动> 真的做了（改动见下）。请判断：按你刚才的分析，
哪几条判据应该变红？如果实际输出里它们没红，最可能的原因是什么？
```

**验收**：至少有一条判据在"故意做错"时红过，并且你把这个负对照写进了自检脚本。
本仓库的做法：`pynq_overlay.py --selftest` 里 4 个用例有 3 个是负对照
（读回全 0 / DMA 少搬一个数 / 逻辑错一位），`pynq_selftest.py` 13 个用例里有 5 个是
"必须失败"的。

**禁止**：

- 不许把"下载成功""灯亮了""没报错"当成判据；
- 不许用墙上时间或人工观察当判据（见 `pitfalls_pynq.md` PYNQ-07）；
- 不许在没跑过负对照的情况下说"已验证"。

**失效条件**：当判据本身依赖板上资源（如真实传感器）时，"故意做错"可能代价很高；
此时退一步做"部分证伪"——把输入钳死成常数，验证输出是否随之变化（不变就是没接通）。
