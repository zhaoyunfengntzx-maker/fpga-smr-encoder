# 技能包 7：仓库可复现性与命名合规

## 1. 一句话 / 解决什么问题

**"能否复现"是竞赛里用提交物直接判分的两项之一**，而它最先死在最便宜的地方：
中文文件名、缺一个入口脚本、报告里写着的数字和仓库里的产物对不上。
本技能给出一个可执行的检查清单：每一条都能用一条命令或一次人工动作验证，
而不是"我们注意了命名规范"。

## 2. 适用范围

- 任何竞赛 / 交付 / 需要别人"从零复现"的工程。
- 任何有多个文档互相引用（`README.md` 指向 `docs/…`，文档指向产物）的仓库。
- 不适用：一次性实验仓库（跑完就丢）——但如果你打算把结果写进报告，那它就不是一次性的。

## 3. 使用方法（逐条可验收）

### 3.1 命名：所有目录名与文件名只用英文

判据（在仓库根目录执行）：

```powershell
# 列出所有"跟踪在版本库里的"非 ASCII 路径 —— 只报错，不改名
git ls-files | Where-Object { $_ -match '[^\x00-\x7F]' }
```

要求：**输出为空**。若不空，按"影响面"从大到小改：

| 优先级 | 类别 | 处置 |
|---|---|---|
| 1 | 核心交付物（设计报告、选题说明、证据索引） | **必改**，并同步所有交叉引用 |
| 2 | 文档主体（`docs/` 全部） | **必改**，README 与文档间的互引一并改 |
| 3 | 被代码引用的文件（接口契约、夹具、日志路径） | **必改**，先 grep 引用点 |
| 4 | 第三方原始资料（数据手册 PDF、厂商指南） | **建议移出提交仓库**（复现不需要它们） |
| 5 | 运行时产物（导出的 PNG、exe、临时目录） | 改，或加进 `.gitignore` |

★ 注意**全角括号、空格、`'`、`&`** 都算"特殊字符"：厂商资料目录里那份
「操作指南（中文）」PDF（本工程已连同其所在目录移出仓库、放 `_refs/vendor/`，见下）
这类名字同时踩两条。
★ 改名前先 `git mv`（保留历史）；改名后**立刻 grep 旧名**，确认没有残留引用。
★ **"仓库内"三个字只覆盖提交进去的东西**：本工程把 3 个非 ASCII 的**根级目录/文件**
（信号源手册目录、示波器手册目录、正点原子 FPGA 开发指南 PDF）整条写进 `.gitignore`
后，`git ls-files` 判据就干净了 —— 但**评审如果直接翻你拷给他们的那个文件夹**，
看到的仍是中文名。所以真正的做法是**二选一**：要么把它们移到仓库外，
要么按上表改 ASCII 名（本工程选了前者，理由见 `NOTICE`）。

### 3.2 单一入口：别人第一条命令就应当能跑

- 根目录 `README.md` 必须包含**按顺序的编号步骤**，每步一条可直接复制的命令。
- 所有脚本里的路径必须是**相对路径**或用 `$PSScriptRoot` / `__file__` 推导，
  不允许出现作者机器的绝对路径（`C:\Users\…`、`D:\Vivado\…` 都要改成可配置项）。
- 第三方工具版本要写清（本工程：Vivado / Vitis **2026.1**）。
- 环境依赖要写清"不需要什么"同样重要（本工程：**不需要 PYNQ、不需要 PS、不需要 DDR3**）。

### 3.3 文档数字与产物的一致性

- 报告里的每个关键数字都要能追到**一个产物文件 + 一个时间戳**（本工程做法：`_synth_work/impl_util.rpt`、
  `impl_timing.rpt`、`sim/logs/SUMMARY.md`、位流文件名+大小+SHA256）。
- 产物更新后，用技能 6 §3.3 的同步脚本刷新文档，并用 `--audit` 检查漏改。
- **历史口径要有意保留并标注"已作废"**，而不是删掉：删掉之后，"为什么这一版和上一版不一样"
  就再也答不出来了。

### 3.4 合规判据清单：每一条都必须**真的跑一遍**

判据不是写给人看的，是**给命令跑的**。本工程在这上面栽过一次：把"厂商手册移出仓库"
写进了 `NOTICE`/`README`/`DEV_STATUS`，而正确的自查命令 `git ls-files "*.pdf"`
**一次都没执行** —— 结果那些文件其实**一直被 git 跟踪着**（详见 `docs/ai-collaboration-log.md` 记录 11）。
把判据写成可直接粘贴的**单行命令**，并在交付前逐条跑、把输出贴进日志：

```bash
# ① 仓库内无中文名（输出必须为空）
git ls-files | grep -P '[^\x00-\x7F]'
# ② 厂商/第三方材料不在版本库里（三条都必须为空输出）
git ls-files _refs
git ls-files '*.pdf' '*.xls' '*.xlsx' | grep '^_refs/'
git rev-list --objects main | grep -iE 'TW28_datasheet|HSTAD9238|AD9238V11|Davinci_Lite|_refs/vendor|引脚映射表|IO引脚分配表'
# ③ 许可证与声明在根目录
ls -l LICENSE NOTICE
# ④ 敏感/超大产物没混进来（>20 MB 应逐个确认过）
git ls-files -z | xargs -0 -I{} sh -c 'test -f "{}" && [ $(stat -c%s "{}") -gt 20971520 ] && echo "{}"'
# ⑤ 工作区干净（提交前）
git status --porcelain
```

★ **两条最容易错的**：
- **`.gitignore` 不能"移出"已被跟踪的文件。** 要真移出，必须
  `git rm --cached <path>`（保留本地文件）—— 加 `.gitignore` 规则只对**尚未被跟踪**的东西有效。
- **从索引移除 ≠ 从历史移除。** 已经提交过的文件仍在旧提交里，
  `git ls-tree -r <旧提交>` 依然能列出它 ⇒ **克隆的人照样拿得到**。
  要对外开源且必须剔除，就得重写历史（`git filter-repo`，或内置的 `git filter-branch`），
  并在**没有 remote** 或已协调好的前提下做（本工程的做法与命令见 `NOTICE` §1.1）。
- **"克隆会拿到什么"的正确判据是把 ref 写死的那条**：
  `git rev-list --objects main | grep -iE '<厂商路径特征串>'`。实测两条反例：
  ① 用 `--all` 会把**本机的链接工作树 HEAD**（`git worktree` 的 detached HEAD）也算作
     可达根 ⇒ 明明 `main` 已经干净，`--all` 仍会打出旧提交，于是判据永远"不通过"；
  ② 特征串写得太宽（例如只写 `TW28`）会命中仓库里**自建的**摘录文档
     （`docs/TW28_digest.md`）⇒ 判据同样永远不可能为空。
  ⇒ 判据要"**对着正确的作用域 + 够精确的特征串**"写，并在写完的当天跑一遍：
  本工程这两条错都是**跑判据时才暴露**的。
- **备份不能放在被重写的仓库里。** 重写前若用 `git branch backup-before-filter` 备份，
  再执行 `git filter-branch … --all`，`--all` 会**把这个备份分支本身也一起重写**，
  备份形同虚设；同理 `refs/original/*` 也要显式删除，否则旧提交仍被 ref 钉住。
  正确做法：`git bundle create <仓库外路径>/backup.bundle --all`（或直接复制整个目录）。

### 3.5 交付物清单逐项打勾（本工程版本）

```text
[ ] 工程包：rtl/ sim/ constr/ host/ model/ tools/ 全部入库，无本地绝对路径
[ ] 仿真或验证结果：sim/logs/SUMMARY.md（PASS n / 共 m）+ 逐台日志
[ ] 综合与实现报告：资源占用、时钟频率、WNS/TNS、位流大小与哈希
[ ] 上板工程与运行脚本、实测输出与参考结果的比对数据
[ ] 可复现的构建脚本（一条命令能重跑仿真与实现）
[ ] 技能包 skill/（本目录）
[ ] 设计报告 + 大模型协作记录
[ ] 开源仓库 + 允许再分发的协议（MIT / Apache-2.0）
[ ] 一页英文 PPT 海报（决赛现场用，A4 彩打）
```

### 3.6 答辩自检：三个最容易被问倒的地方

1. **"你说必须用 FPGA，为什么？"** —— 准备好**定量对比**（MCU 的方案为什么做不到、专用芯片为什么不够），
   而不是"FPGA 快"。
2. **"这个数字是实测还是仿真？"** —— 报告里每个数字旁边标 `[实测]` / `[仿真]` / `[手册]`。
   混在一起是重灾区。
3. **"你的负余量 / 未达标项怎么解释？"** —— 主动写清楚边界条件（本工程的范例：
   "负值里约 3 ns 是相位口径错误，其余是真实建模余量"），比藏着不说安全得多。

## 4. 失效条件

- 本技能是**交付前检查**，不能替代工程本身：命名全英文、文档齐全，
  但功能没跑通，仍然是"完整度"直接判低。
- 改名是**破坏性操作**：必须先 `git mv`、然后 grep 旧名、然后重新跑一遍回归与文档构建
  （本工程的 PDF 生成脚本 `tools/md2pdf.py` 会写 `_pdf_out/*.html`，也要一并处理）。
- 开源协议的选择要与依赖一致：若工程内嵌了第三方源码/资料，需先确认其许可允许再分发。
- 清单会过时：指南里的权重与条目每年可能变（本工程记录的是 2026 年自主选题赛道口径），
  交接时要重新对照当年的官方文本。

## 5. 提炼过程（从哪些失败或观察中总结）

1. **本仓库实测有 52 个文件名的非 ASCII 路径**（已排除 `_tools` / `_synth_work` / `_v11_verify` /
   `dist*` / `build` / `.git` 等构建缓存目录，统计范围 15,330 个文件），
   其中包含**核心交付物**：设计报告、选题说明、证据索引，以及整个 `docs/` 主体与接口契约文档。
   ⇒ 这不是"风格问题"，是"复现性"这一项的直接扣分点；而且它**不会在功能测试里暴露**，
   只能靠一次专门的检查发现。
2. **同一指标散落在多处文档、口径不一**：本工程曾出现"同一个总输入延迟数字在 5 处文档里
   与手册口径混称"的问题，五处统一改写后才消除。
   ⇒ 由此产生了"文档数字同步脚本 + `--audit` 保留历史映射"的做法。
3. **两条必交物曾经缺失**：技能包目录曾**完全不存在**（本目录就是补上的），
   大模型协作记录也只在 `DEV_STATUS.md` 里以流水形式存在、没有成文。
   这两项合计 **15/100 的权重**，而补齐它们**只需要整理已经发生过的事情**。
4. **沙箱/工具链会制造"假失败"**（详见技能 6 §5）：构建脚本 `exit 1` 不等于构建失败。
   ⇒ 因此"可复现"清单里必须包含"**用产物时间戳与哈希判断是否真的写完了**"这一步，
   否则接手人会在一个假失败上耗掉一整天。

**可直接借用的动作清单**：
① 把 §3.1 的 `git ls-files` 命令加进你的提交前检查（输出必须为空）；
② 脚本里禁止绝对路径——用 `$PSScriptRoot` / `__file__`；
③ 报告数字必须能追到"产物文件 + 时间戳 + 哈希"；
④ 改名后立刻 grep 旧名并重跑一次回归。
